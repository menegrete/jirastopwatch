## Context

Currently, `maxIssues` is a hardcoded constant in MainForm.cs (line 767: `private const int maxIssues = 20;`). The application uses a three-tier settings architecture:
1. **Properties.Settings.Designer.cs** (auto-generated): Defines application settings with defaults
2. **Settings.cs**: Wrapper class that reads/writes to Properties.Settings
3. **SettingsForm.cs**: UI dialog where users edit settings

The application persists user settings to `%APPDATA%\Jira StopWatch` using .NET's application settings infrastructure.

## Goals / Non-Goals

**Goals:**
- Enable users to configure max issues limit independently (1-40 range)
- Persist the setting across application sessions
- Setting takes effect immediately without app restart
- Maintain backward compatibility (new setting defaults to current limit of 20)

**Non-Goals:**
- Adding UI constraints visualization (e.g., showing "you're at 15/30 issues")
- Dynamic adjustment of UI layout based on screen size
- Adding per-project or per-filter issue limits (global limit only)

## Decisions

### Decision 1: Store MaxIssues in Properties.Settings with default of 20

**Approach:** Add a new `int MaxIssues` property to Settings.Designer.cs with default value "20", matching the pattern of other settings like `IssueCount`.

**Rationale:**
- Consistent with existing architecture - all user preferences use this pattern
- Automatic persistence to user's roaming profile (Windows Registry or XML file per OS)
- Survives application upgrades via the upgrade/reload mechanism

**Alternatives Considered:**
- Config file in app directory: Would break per-user settings and complicate installation
- In-memory only: Would require reload on settings change, contradicts requirement #3

### Decision 2: Add NumericUpDown control to SettingsForm with validation

**Approach:** Add a NumericUpDown control bound to Settings.MaxIssues with:
- Minimum: 1
- Maximum: 40
- No decimal places
- Label: "Maximum issues to display"

**Rationale:**
- NumericUpDown enforces bounds at UI level - users cannot enter invalid values
- Clearer than text input for integer constraints
- Consistent with Windows Forms conventions for numeric input

**Alternatives Considered:**
- Text input with validation: More error-prone, requires user education on constraints
- Slider: Harder to see exact value; 40 is too wide for effective slider UX

### Decision 3: Apply setting dynamically - no app restart needed

**Approach:** MainForm reads `settings.MaxIssues` at initialization and when processing the add-issue button. When SettingsForm closes with OK, MainForm calls `InitializeIssueControls()` which already handles dynamic re-layout.

**Rationale:**
- Users expect immediate effect per spec requirement "takes effect immediately"
- InitializeIssueControls() already recalculates UI bounds and button state
- No additional code needed beyond wiring the setting through

**Alternatives Considered:**
- Force restart: Would be jarring and violate user expectations
- Apply only on next launch: Inconsistent with how theme changes work (already dynamic)

## Risks / Trade-offs

**[Risk]** Users who set MaxIssues very high (e.g., 40) with many issues loaded may experience performance degradation or window height exceeding screen bounds.
→ **Mitigation:** Hard cap of 40 provides reasonable protection. Window auto-repositioning (lines 416-421 in MainForm) prevents falling off-screen. Users can still scroll.

**[Risk]** If Settings.Designer.cs is regenerated by Visual Studio, the new MaxIssues property could be lost.
→ **Mitigation:** This is auto-generated code but changes are typically preserved by Visual Studio tooling. The property follows exact pattern of existing settings. If lost, the .openspec.yaml can document the change for easy re-application.

**[Risk]** Existing user configurations with IssueCount > 20 (e.g., from an older version) may be incompatible with new MaxIssues default of 20.
→ **Mitigation:** Application already handles this in MainForm lines 346-349 (caps IssueCount to maxIssues). Same logic applies here - no behavior change.

## Implementation Note

The change is scoped to:
1. **Settings.Designer.cs**: Add MaxIssues property
2. **Settings.cs**: Add property and sync logic  
3. **SettingsForm.cs**: Add NumericUpDown control and binding
4. **MainForm.cs**: Replace 5 references to hardcoded constant with settings.MaxIssues

No changes to data models, serialization, or persistence layer required - reuses existing infrastructure.
